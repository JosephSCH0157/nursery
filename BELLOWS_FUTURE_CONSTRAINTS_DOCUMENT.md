# Bellows Future Constraints Document

This document defines the long-term guardrails that Bellows must obey in V2, V3, and beyond.

Purpose:

Bellows must not drift into an incoherent pile of features.

This document exists to prevent Bellows from becoming:

- OBS with more tabs
- a meeting platform
- a social product
- an editor disguised as a studio

## Bellows Must Never Become

### A Meeting Platform

Bellows should not pivot toward large-room conferencing or generic meeting behavior.

### A Social Network

Bellows should not gain:

- feeds
- followers
- engagement mechanics

### A Full NLE

Editing belongs to Hammer.

Bellows is not the place for full editorial assembly.

### A Graphics Workstation

Complex visual production tooling belongs downstream, not in the capture studio.

### A Platform Hostage

Bellows must not become dependent on any single external service for core functionality.

### A Plugin Jungle

Extensibility must not compromise reliability or operational clarity.

## Growth Philosophy

Bellows should grow by:

- deepening reliability
- expanding professional use cases
- improving capture quality
- strengthening integrations

Bellows should not grow by:

- chasing consumer features
- copying competitors mechanically
- adding superficial capability for its own sake

## Feature Admission Test

Before adding a feature, Bellows should be tested against the following questions:

- does this improve production reliability
- does this reduce Host stress
- does this preserve simplicity during live mode
- does this belong at capture time rather than editing time
- would removing it later break Bellows identity

If most answers are no, the feature probably does not belong.

## Compatibility Promise

Future versions must preserve:

- session integrity guarantees
- local-first safety
- Host authority model
- guest simplicity
- clear recording truth

Breaking these breaks trust.

## Canonical Constraint Principle

Bellows should become deeper, not wider.
